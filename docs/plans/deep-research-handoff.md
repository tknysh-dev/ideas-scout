# План: глибоке дослідження через ручний handoff

Статус: узгоджено з власником 2026-08-04. Виконавець працює по фазах; після
кожної фази — коміт (нічний `runner.sh` відкочує некомічені зміни в
`agents/scripts/` і `shared/migrations/` — незакомічена робота там згорить).

## Мета

Автоматичний мульти-CLI конвеєр глибокого дослідження виявився неживучим:
з CLI повноцінний веб-пошук має лише Codex (Gemini на безкоштовному плані без
search, DeepSeek віддає кешоване). Переходимо на ручний handoff: власник
копіює згенерований промт у браузерні deep-research UI кількох LLM
(ChatGPT, Gemini, Perplexity, Grok…), збирає відповіді й вставляє їх одним
блобом назад на портал; Claude на M1 консолідує. Глибоке дослідження робиться
рідко і лише для вагомих ідей, тому ручний цикл прийнятний.

Ключові узгоджені рішення:

1. **Один промт — весь пакет.** Зовнішня модель за один прогін віддає і базові
   критерії, і d_-блоки, і конкурентів. Окрема CLI-стадія `competitors` зникає
   (разом із short-exit «конкуренти лише якщо фатальні пройдено»).
2. **Claude не дублює дослідників.** По базових критеріях він лише адʼюдикує
   чужі докази; власний веб-пошук робить тільки по d_-блоках (їх не було в
   початковому аналізі). Окремої вкладки-дослідника для Claude немає.
3. **Синтез — два послідовні виклики**, щоб одна відповідь не обрізалась.
4. **Вкладки моделей** показують структуровані вердикти (summary/detail/
   evidence) — сирий прозовий звіт в UI не потрібен (але зберігається в
   `research_reports` як джерело правди для синтезу).
5. **Ліміт звіту** ~3000 слів — інакше 4–5 звітів не влізуть у консолідатор.

## Цільовий потік

```
Портал: «Опції» → «Промт для глибокого дослідження»
  └─ бекенд генерує промт (контекст ідеї + чек-лист + d_-блоки + конкуренти)
  └─ власник копіює, вставляє в N браузерних UI, чекає deep research
Портал: «Опції» → «Консолідувати відповіді»
  └─ textarea: всі звіти одним блобом
  └─ бекенд ріже по маркерах, валідує JSON, показує розбір ДО запуску
  └─ підтвердження → пише research_reports + criteria_verdicts (kind=model)
                   → створює job deep_research_synthesis
M1 (job-worker): deep-research.py --stage synthesis
  └─ виклик A (Claude): власне дослідження d_-блоків + адʼюдикація критеріїв
  └─ виклик B (Claude): фінальний текст картки + зведення конкурентів
  └─ пише criteria_verdicts (kind=synthesis), competitors, оновлює ideas
Портал: сторінка ідеї — консолідований результат + таби моделей + конкуренти
```

## Фаза 1 — Зрозуміла термінологія і статуси

Проблема: власник не розуміє формулювань «дослідник», «обидві сторони»,
«консенсус», «за доказами», «Із зауваженням», злипле «консенсус4/5».

### 1.1 UI-словники — `dashboard/src/lib/deep-research.ts`

- `RESOLUTION_META`: людські підписи, які читаються без контексту:
  - `consensus` → «Моделі зійшлись»
  - `evidence` → «Вирішено перевіркою джерел»
  - `cross_exam` → «Вирішив арбітражний раунд»
  - `pessimistic_default` → «Взято найгірший варіант»
  Хінти переписати повними реченнями, зрозумілими не-експерту.
- `TONE_META.noted` → підпис на кшталт «Пройдено із застереженням» (означає:
  вердикт не фатальний, але є зауваження, яке варто прочитати).

### 1.2 Рендеринг — `dashboard/src/components/VerdictDetails.tsx`

- Пояснення резолюції показувати видимим текстом під плашкою (зараз лише
  `title`-hover, на мобільному недоступний).
- Оцінку відділити від плашки резолюції: окремий елемент «Оцінка: 4/5»
  (виправляє злипання «консенсус4/5»).
- Плашки моделей підписувати явно: «Codex: Пройдено» лишити, але додати
  (один раз на секцію, не на кожен критерій) вступний рядок: «Нижче — як
  проголосувала кожна модель-дослідник і як зведено розбіжності».

### 1.3 Легенда

- У секції глибокого дослідження (початок `CriteriaAnalysis` або окремий
  компонент) — згорнутий блок «Як читати ці статуси»: перелік усіх плашок
  (вердикти, резолюції, «моделі розійшлись») з поясненням в одне речення.
  Один раз на сторінку, розгортається по кліку.

### 1.4 Проза синтезу — `agents/prompts/deep-research-synthesis.md`

- У правила `criteria_section_md` і `detail` додати: заборонено слова
  «дослідник», «сторони», «арбітр» без імені; учасників називати явно —
  «Codex», «Gemini», «ChatGPT», «початковий аналіз (швидка перевірка Claude
  без глибокого пошуку)». Замість «Обидві сторони дали B» → «І початковий
  аналіз, і Codex оцінили довіру до джерела на B».
- Зафіксувати: уже збережені тексти існуючих карток це не виправить — лише
  нові прогони.

### Критерій приймання

На сторінці ідеї з наявними даними глибокого дослідження всі плашки читаються
без hover'а і без знання внутрішньої кухні; оцінка не злипається з резолюцією;
легенда пояснює кожен можливий статус.

## Фаза 2 — Таби моделей і акордеони конкурентів

### 2.1 Таби по моделях

Дані вже є в `criteria_verdicts` (`stage='deep'`, `kind='model'`, поле
`provider`) — `groupVerdicts()` у `lib/deep-research.ts` їх уже групує.

- Новий клієнтський компонент (наприклад `DeepResearchTabs.tsx`) на сторінці
  ідеї `app/ideas/[id]/page.tsx`:
  - Зверху — консолідований результат (як зараз: розділ «Аналіз за
    критеріями» з тексту картки + синтез-вердикти). Він і є «головна правда».
  - Під ним — таби, по одному на `provider` (naturally: Codex, Gemini,
    ChatGPT, Perplexity…). Наявний `components/Tabs.tsx` працює через
    `href` (URL-параметр) — або переюзати з `?tab=`, або зробити локальний
    стейт-варіант без навігації (краще: стейт, щоб не смикати сервер).
  - Вміст вкладки: всі критерії і d_-блоки цієї моделі — вердикт-плашка,
    score, summary, detail (згорнутий через `CollapsibleBody`), evidence
    (лінки з датами) — переюзати розмітку `VerdictDetails`, але для одного
    провайдера.
- Плашки «як проголосували моделі» в консолідованій частині лишаються — вони
  тепер ще й підказка, в яку вкладку глянути.

### 2.2 Конкуренти акордеонами — `components/CompetitorsSection.tsx`

- Кожен конкурент — акордеон: згорнутий стан показує лише назву (лінком, як
  зараз) + плашку «Живий/Застиг/Мертвий». Розгорнутий — усе інше: pricing,
  остання активність, сильні/слабкі сторони, кут відриву, докази.
- Розгортання незалежне по кожному; компонент стає клієнтським (стейт) або
  використовує `<details>`. Звірити стиль з наявним `CollapsibleBody`.
- Підсумковий рядок «Живих: X · Застиглих: Y · Мертвих: Z» лишити над списком.

### Критерій приймання

Сторінка ідеї з глибоким дослідженням: консолідований блок зверху, таби
дають повний перегляд внеску кожної моделі; список конкурентів компактний,
деталі відкриваються по кліку.

## Фаза 3 — Єдиний handoff-промт і демонтаж CLI fan-out

### 3.1 Новий промт-шаблон — `agents/prompts/deep-research-handoff.md`

База — `deep-research-researcher.md` (роль, безпека, датовані докази,
чек-лист, d_-блоки, JSON-схема criteria). Зміни:

1. **Ідентифікація** (на початку):
   - Плейсхолдер `{{RESEARCHER_LABEL}}` — його вписує власник перед вставкою
     («ChatGPT», «Gemini» …). Якщо порожній — модель використовує власну
     назву продукту.
   - Обгортка відповіді маркерами (перший і останній рядки):
     `===== DEEP RESEARCH REPORT START | {{RESEARCHER_LABEL}} | {{IDEA_ID}} =====`
     … `===== DEEP RESEARCH REPORT END =====`. Без маркерів звіт не буде
     оброблено — сказати це моделі явно.
2. **Режим «тільки живий пошук»**: якщо веб-пошук недоступний — не відповідати
   по суті, а вивести всередині маркерів один рядок `SEARCH UNAVAILABLE`.
   Відповідь з памʼяті гірша за відсутність відповіді.
3. **Блок конкурентів**: до завдання додається пошук конкурентів ніші
   (переюзати вимоги з `deep-research-competitors-researcher.md`: назва, url,
   цінова модель, liveness-сигнали, остання активність, сильні/слабкі,
   докази з датами).
4. **Формат відповіді**: прозовий звіт українською (ліміт ~3000 слів), потім
   РІВНО ОДИН fenced `json`-блок:

   ```json
   {
     "researcher": "{{RESEARCHER_LABEL}}",
     "self_reported_model": "як модель сама себе називає",
     "criteria": [ /* як у researcher-промті: criterion_key, verdict, score,
                      summary, detail, evidence[] */ ],
     "competitors": [ /* name, url, pricing, liveness, last_activity,
                         strengths, weaknesses, differentiation, evidence[] */ ]
   }
   ```

   Один JSON-блок (не два) — щоб парсинг був однозначним.

### 3.2 Генерація промта

- Логіку підстановки плейсхолдерів (`{{IDEA_CONTEXT}}`, `{{CRITERIA_DOC}}`,
  `{{DEEP_DOC}}`, `{{TODAY}}`, `{{EXPECTED_COUNT}}`…) винести з
  `deep-research.py` так, щоб нею міг користуватись і дашборд. Варіанти:
  (а) серверний код дашборда збирає промт сам із файлів репо + даних БД;
  (б) `deep-research.py --stage render-prompt` віддає готовий промт.
  Дашборд не має доступу до файлової системи M1 у рантаймі? — Має: дашборд
  деплоїться з того ж репо, файли промтів доступні через `fs` у Server
  Action / route handler. Обрати (а): TypeScript-порт підстановки в
  `dashboard/src/lib/` (це ~50 рядків: читання шаблону, контекст ідеї з БД,
  вставка документів критеріїв). `IDEA_CONTEXT` збирати так само, як
  `load_idea()` у `deep-research.py`.
- `{{RESEARCHER_LABEL}}` лишається літеральним плейсхолдером у скопійованому
  тексті — власник заповнює його руками (або лишає порожнім).

### 3.3 Демонтаж старого fan-out — `agents/scripts/deep-research.py`

- Видалити: паралельний прогін дослідників через `llm-invoke.sh`
  (`run_researchers`), крос-допит DeepSeek, стадію `competitors` як окремий
  CLI fan-out, `enqueue_competitors()` і short-exit логіку
  (`all_fatal_passed → enqueue`).
- Лишити і переюзати: `load_idea`, санітизацію (`VERDICTS`, `DEEP_KEYS`,
  білі списки, `sanitize_competitors`), `extract_json_block`, запис у БД,
  `replace_section`, оновлення `ideas` і `events`.
- Нова стадія `--stage synthesis` (деталі у фазі 4) — єдина точка входу.
- `agents/worker/job-worker.mjs`: прибрати handler `deep_research_competitors`,
  додати `deep_research_synthesis` (і пропуск payload у рядку ~90).
  Тип job `deep_research` (авто-прогін) вимкнути або лишити як legacy —
  рішення: видалити handler, щоб не було двох шляхів.
- `db.sh::db_deep_research_health`, `doctor.sh` (рядок ~309 і чеки глибокого
  дослідження), `docs/operations.md`, `shared/contracts.md` — оновити під
  нові типи job і потік. Документація не має брехати.
- `llm-invoke.sh`: лишається лише для Claude (синтез). Гілки gemini/deepseek/
  codex можна лишити, але з контрактів прибрати згадки про них як дослідників.

### Критерій приймання

Промт генерується і містить усе (критерії + d_-блоки + конкуренти + маркери +
анти-кеш правила); старий авто-fan-out недосяжний ні з дашборда, ні з черги;
doctor/контракти/док-и відповідають новій схемі.

## Фаза 4 — Синтез у два виклики Claude

### 4.1 Вхід стадії `--stage synthesis`

- Payload job: `{"idea_id": "..."}`. Джерело правди — БД:
  - `research_reports` (`stage='deep_criteria'`, `kind='model'`) — вставлені
    дашбордом вербатим-звіти зовнішніх моделей;
  - з кожного `report_md` витягнути `json`-блок (`extract_json_block`) —
    criteria + competitors кожної моделі;
  - початковий аналіз ідеї — як зараз (`IDEA_SNAPSHOT`).

### 4.2 Виклик A — прогалини + адʼюдикація

Промт (оновлений `deep-research-synthesis.md`):

- По **базових критеріях**: лише адʼюдикація чужих звітів проти початкового
  аналізу за наявними правилами (докази без дати не існують; консенсус;
  перевірка джерел; песимістичний дефолт для фатальних). Крос-допит-розділ
  видалити (арбітра більше немає) — `resolution='cross_exam'` лишити в БД
  для сумісності зі старими рядками, але з нових промтів прибрати.
- По **d_-блоках**: спершу ВЛАСНЕ глибоке веб-дослідження (WebSearch/WebFetch)
  кожного блоку — це заповнення прогалини, бо початковий аналіз d_-блоків не
  мав; потім зведення власних знахідок зі звітами моделей. До власних
  знахідок — ті самі вимоги (URL + дата), щоб компенсувати ухил «свій звіт
  правильніший».
- Вихід A: `criteria[]` (усі базові + d_) + `idea_updates` (як зараз).
- Правило іменування учасників з фази 1.4 діє.

### 4.3 Виклик B — текст картки + конкуренти

- Вхід: результат виклику A + списки конкурентів з усіх звітів + поточне body.
- Вихід: `criteria_section_md` (повний текст розділу «Аналіз за критеріями»),
  `competitors[]` (канонічний дедуплікований список — логіка з нинішнього
  промта `deep-research-competitors-synthesis.md`: злиття дублікатів,
  liveness за доказами), `competitors_section_md`, `summary`.
- Суперечність критерію насиченості → `ceiling_flag='review'` (як зараз у
  стадії competitors).

### 4.4 Запис результатів

- Виклик A → upsert `criteria_verdicts` (`kind='synthesis'`), звіт у
  `research_reports` (`kind='synthesis'`, `provider='claude'`).
- Виклик B → перезапис `competitors` ідеї, розділи body («Аналіз за
  критеріями», «Конкуренти»), оновлення `ideas` (research_depth, verdict_*,
  rejection_*, deep_researched_at, deep_research_run_id,
  `verdict_model = 'synthesis:claude+' + мітки дослідників`), подія в `events`.
- Без short-exit: обидва виклики виконуються завжди, навіть якщо фатальні
  критерії провалені (ідея може отримати rejection_code, але повний пакет —
  конкуренти, економіка — все одно записується).
- Таймаути: A і B — окремі `SYNTHESIS_TIMEOUT_S`; A з реальним пошуком —
  збільшити дефолт (пропозиція: 2700с).

### 4.5 Preflight веб-пошуку Claude — `doctor.sh`

- Новий чек: `llm-invoke.sh run claude` з міні-промтом, що вимагає знайти
  через веб-пошук факт, якого нема в тренувальних даних (наприклад,
  сьогоднішню дату з живої сторінки або заголовок свіжої новини з URL),
  і повернути URL + дату. Якщо відповідь без URL або з відмовою — чек
  червоний: «синтез робитиме кешовані d_-блоки». Чек позначити як повільний/
  опційний (окремий прапорець doctor), щоб не ганяти LLM на кожен прогін
  doctor.

### Критерій приймання

Job `deep_research_synthesis` на ідеї з ≥1 звітом у `research_reports`
проходить обидва виклики, пише синтез-вердикти по всіх критеріях і d_-блоках,
оновлює конкурентів і body; при провалених фатальних критеріях конкуренти й
d_-блоки все одно заповнені; doctor ловить відсутність пошуку в Claude.

## Фаза 5 — UI handoff на порталі

### 5.1 Кнопка «Опції» на сторінці ідеї

- Замість (або поруч зі старою кнопкою запуску глибокого дослідження — стару
  прибрати, бо авто-конвеєра більше немає) — dropdown «Опції»:
  1. «Скопіювати промт глибокого дослідження» — Server Action / route
     генерує промт (фаза 3.2), клієнт кладе в буфер обміну
     (`navigator.clipboard.writeText`), тост «Промт скопійовано (N символів)».
  2. «Консолідувати відповіді…» — відкриває форму консолідації (5.2).
- Доступність пунктів — та сама перевірка статусу, що в
  `enqueueDeepResearch` (`OWNER_DECIDABLE_STATUSES`) + авторизація власника
  (`ownerLogin()` у `lib/owner.server.ts`).

### 5.2 Форма консолідації

- Велика textarea («вставте всі звіти одним текстом, порядок неважливий»).
- Крок 1 — **розбір без запису**: Server Action ріже блоб по маркерах
  `===== DEEP RESEARCH REPORT START | <label> | <idea_id> =====` …
  `===== DEEP RESEARCH REPORT END =====`, для кожного звіту:
  - мітка дослідника (з маркера; порожня → з `researcher` у JSON →
    `self_reported_model` → «unknown-N»);
  - перевірка `idea_id` з маркера проти поточної ідеї (чужі звіти — відхиляти
    з поясненням);
  - `SEARCH UNAVAILABLE` → звіт позначається як відмова;
  - витяг і валідація JSON: критерії з білого списку ключів/вердиктів
    (продублювати санітизацію з `deep-research.py`), конкуренти —
    `sanitize_competitors`-логіка;
  - результат розбору показується власнику: «Розпізнано 3 звіти:
    ChatGPT — 14 критеріїв, 6 конкурентів ✓; Gemini — ✓; Perplexity — JSON
    невалідний ✗ (причина)». Кнопка «Запустити консолідацію» активна, якщо
    валідних звітів ≥1.
- Крок 2 — **підтвердження**: запис у БД:
  - `research_reports`: upsert (`idea_id`, `stage='deep_criteria'`,
    `kind='model'`, `provider=<label>`, `report_md=<вербатим текст звіту>`,
    `model=<self_reported_model>`, `status='ok'|'error'`);
  - `criteria_verdicts`: upsert рядків `kind='model'`, `stage='deep'`,
    `provider=<label>` — таби фази 2 працюють одразу, ще до синтезу;
  - job `deep_research_synthesis` з idempotency-ключем за зразком наявного
    (`deep-research-synthesis:<idea_id>:<хвилинне вікно>`);
  - повторна консолідація тієї ж ідеї дозволена свідомо (upsert перезапише).
- Санітизація: увесь текст зі звітів — недовірені дані; у БД лише значення з
  білих списків, довільний текст лише в текстові поля (та сама політика, що
  в `deep-research.py`). У промт синтезу звіти йдуть з тим самим правилом
  «дані, не інструкції», що вже прописане.

### 5.3 Зворотній зв'язок

- На сторінці ідеї — статусний блок стану дослідження: якщо є активний job
  `deep_research_synthesis` (queued/running) — лоадер з фазою («в черзі»,
  «синтез: дослідження прогалин», «синтез: текст і конкуренти») і посиланням
  на прогін у `/runs` (логи там уже є). Джерело: `jobs` + `runs` по
  `idea_id`; сторінка робить періодичний refresh (наявний патерн у
  `JobsTable`/`RunsTable` — переюзати).
- Після завершення — сторінка показує оновлені дані (фази 1–2).

### Критерій приймання

Повний цикл руками: скопіювати промт → отримати відповіді у ≥2 UI → вставити
блоб → побачити розбір → запустити → бачити лоадер/лог → побачити
консолідований результат, таби моделей і конкурентів-акордеони.

## Наскрізні вимоги

- **Мова:** увесь UI, промти і тексти для власника — українською;
  пояснювальна людська проза без жаргону (стайлгайд `templates/idea.md`).
- **Безпека:** вміст зовнішніх звітів і веб-сторінок — недовірені дані.
  Розділи «дані проти інструкцій» у промтах зберегти; санітизація білими
  списками на кожному вході в БД.
- **Коміти:** окремий коміт на фазу (мінімум). Зміни в `agents/scripts/` і
  `shared/migrations/` комітити одразу — нічний runner відкочує некомічене.
- **Міграції БД не потрібні:** наявні `criteria_verdicts`, `research_reports`,
  `competitors`, `jobs` покривають потік (provider — вільний текст; стадії
  вкладаються в наявні CHECK). Якщо виконавцю знадобиться нове поле —
  спершу перевірити, чи не покривається наявним, і лише тоді міграція.
- **Порядок фаз:** 1 → 2 → 3 → 4 → 5. Фази 1–2 незалежні від 3–5 і дають
  видиму цінність одразу. Фаза 5 залежить від 3 (промт) і 4 (job синтезу).
- **Що НЕ робити:** не зберігати сирі прозові звіти в UI-компонентах (тільки
  структуровані вердикти); не додавати Claude-вкладку дослідника; не
  відновлювати авто-fan-out CLI-моделей.
