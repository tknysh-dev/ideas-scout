# Експлуатація ideas-scout: інструкція для власника

Цей документ — не для розробника, а для тебе як власника системи. Він пояснює, що треба зробити один раз перед першим запуском, як прогнати систему вручну, як поставити її на автопілот (launchd), і як читати результати та реагувати на проблеми.

Уся інфраструктура описана тут відповідає `PLAN.md`, розділ «Фаза 6: Інфраструктура виконання» і розділу «Рекомендації рецензії» в кінці того ж файлу — якщо щось тут здається дивним чи надто обережним (наприклад, чому агент не може сам закомітити зміни), причина пояснена там.

## 1. Передумови (зробити один раз, вручну, до першого запуску)

Ці кроки навмисно **не автоматизовані** — вони або торкаються секретів, або потребують твого рішення.

### 1.1. Машина і окремий користувач для агента

Уся система має жити на M1 (постійний воркер, за планом). Не запускай launchd-джоби на випадковій машині — `agents/scripts/install-launchd.sh` навіть попереджає про це текстом при старті.

Система працює під **окремим користувачем macOS** (виконано 2026-07-16: створено Standard-юзера для агента; профілі інших користувачів закриті через `chmod 700 /Users/<профіль>`). Що це дає і що з цього випливає:

- Standard-юзер без адмінправ не може міняти систему і не бачить вміст чужих профілів; агентські прогони ізольовані від твоїх особистих файлів.
- У цього юзера **власний Keychain** — Telegram-токен, покладений під ним, недосяжний з інших профілів (і навпаки).
- Тому **всі наступні кроки цього розділу (1.2–1.6), клон репозиторію і `install-launchd.sh` виконуються залогіненим під цим юзером**, не під твоїм основним: launchd-джоби ставляться в його `~/Library/LaunchAgents`, і Keychain-записи monitor.sh шукатиме саме в його зв'язці.
- launchd-джоби юзера виконуються, коли він залогінений (достатньо fast user switching у фоні); тримай його сесію активною на M1.
- Remote Login/SSH для цього юзера вимкни (System Settings → Sharing), якщо віддалений доступ не потрібен.

### 1.2. GitHub-доступ

```
gh auth login
```

Виконати на M1, під тим акаунтом, яким система коммітитиме й пушитиме. Переконайся, що `git remote -v` у репозиторії показує саме той приватний репозиторій, який очікується.

### 1.3. Telegram-бот (для щоденного дайджесту)

1. У Telegram знайди `@BotFather`, команда `/newbot`, дай боту ім'я — отримаєш токен виду `123456:ABC-DEF...`.
2. Напиши своєму новому боту будь-яке повідомлення (щоб дізнатись свій `chat_id`) — простий спосіб: відкрий `https://api.telegram.org/bot<ТОКЕН>/getUpdates` у браузері після того, як написав боту, і знайди `"chat":{"id": ...}`.
3. Поклади обидва значення в Keychain (НЕ в репозиторій, НЕ в `.env`, НЕ в змінні середовища launchd):

```
security add-generic-password -s ideas-scout-telegram -a ideas-scout -w '<ТОКЕН_БОТА>'
security add-generic-password -s ideas-scout-telegram-chat -a ideas-scout -w '<CHAT_ID>'
```

Перевірити, що записалось (без показу самого секрету — лише факт наявності):

```
security find-generic-password -s ideas-scout-telegram
```

### 1.4. Dead-man's switch (опційно, але рекомендовано)

Рекомендація рецензії: сама відсутність дайджесту в Telegram — ненадійний сигнал проблеми (можеш просто не помітити тишу тижнями). Тому додатково після кожної успішної відправки дайджесту `monitor.sh` пінгує зовнішній сервіс моніторингу (наприклад [healthchecks.io](https://healthchecks.io), безкоштовний план достатній).

1. Зареєструй перевірку (check) на такому сервісі з очікуваним інтервалом ~1 доба (щоб відхилення в межах доби не тригерило зайвих алертів на самому сервісі — він же й сам надішле тобі повідомлення, якщо пінг не прийде вчасно).
2. Отримаєш URL виду `https://hc-ping.com/<uuid>`.
3. Поклади в Keychain:

```
security add-generic-password -s ideas-scout-healthcheck -a ideas-scout -w 'https://hc-ping.com/<uuid>'
```

Якщо цього запису немає — `monitor.sh` просто не пінгує нікуди, без помилки (це опційний крок).

### 1.5. Промпти агентів

`agents/prompts/collector.md` і `agents/prompts/analyst.md` мають існувати й бути закомічені в git **до** першого запуску `runner.sh` — без них прогін одразу завершується статусом `error` (`промпт не знайдено`). Якщо їх ще нема — це окрема робота (Фаза 3/4 плану), не інфраструктурна.

### 1.6. agents/criteria/availability.md

Заповни вручну — скільки часу на тиждень готовий інвестувати в запуск/підтримку нових механік і в які години сам активно працюєш із підписками Claude/Codex (щоб автопрогони не конкурували з тобою за ліміт).

### 1.7. Reddit (опційно)

Reddit — опційне джерело: без нього система просто працює далі на HN, DOU і веб-пошуку (`agents/scripts/reddit-fetch.sh` сам вийде з кодом 0, нічого не зламавши). Якщо хочеш увімкнути:

1. Створи script-застосунок на [reddit.com/prefs/apps](https://www.reddit.com/prefs/apps) — тип **script**, redirect uri можна вказати `http://localhost:8080` (не використовується, потрібен лише як формальність форми).
2. Отримаєш client id (рядок під назвою застосунку) і client secret.
3. Поклади обидва в Keychain:

```
security add-generic-password -U -A -s ideas-scout-reddit-id -a ideas-scout -w '<CLIENT_ID>'
security add-generic-password -U -A -s ideas-scout-reddit-secret -a ideas-scout -w '<CLIENT_SECRET>'
```

Без цих двох записів `agents/scripts/reddit-fetch.sh` виведе «Reddit-креденшели не налаштовані — пропускаю» і вийде з кодом 0 — collector просто відпрацює без Reddit-кешу.

## 2. Ручний прогін

### 2.1. Спочатку dry-run

Dry-run виконує **реальний** лок і **реальну** git-гігієну (stash брудного дерева, спроба `pull --rebase`), але замість виклику CLI й коміту/пушу — лише виводить, що́ було б виконано. Це безпечно ганяти скільки завгодно.

```
./agents/scripts/runner.sh --track passive-income --agent collector --provider claude --dry-run
```

Перевір вивід і `logs/status/passive-income-collector.json` (там буде `"status": "dry_run"`).

### 2.2. Бойовий прогін

```
./agents/scripts/runner.sh --track passive-income --agent collector --provider claude
```

Аналогічно для аналітика (`--agent analyst`).

**Захист робочих годин:** реальний (не dry-run) прогін у робочому вікні (за замовчуванням пн–пт 09:00–19:00) автоматично пропускається зі статусом `skipped_work_hours` — щоб launchd, доганяючи пропущений розклад після сну машини, не спалював ліміт підписки саме тоді, коли ти сам працюєш. Налаштування через змінні середовища: `IDEAS_SCOUT_WORK_DAYS` (дефолт `1,2,3,4,5`, 1=понеділок), `IDEAS_SCOUT_WORK_HOURS` (дефолт `09:00-19:00`; значення `none` вимикає захист повністю). Для разового ручного запуску вдень — `IDEAS_SCOUT_IGNORE_WORK_HOURS=1 ./agents/scripts/runner.sh ...`.

**Про codex — вимкнено за замовчуванням.** `--provider codex` одразу завершується зі `status=error`: `codex exec` навіть у пісочниці (`--sandbox workspace-write`) дає агенту повноцінний shell, а весь захист від промпт-ін'єкції в цій системі тримається на інваріанті «агент без shell» (агент не повинен мати шляху до git, curl чи Keychain). Якщо свідомо приймаєш цей ризик — запусти з явним `IDEAS_SCOUT_ALLOW_CODEX=1`. Додатково: прапорці виклику `codex exec` у `invoke_codex()` **не перевірені живим прогоном** (інсталяція codex була зламана на машині, де це писалось) — перед першим таким прогоном виконай `codex --help` і `codex exec --help` на M1 і звір. За замовчуванням тримайся `--provider claude`.

### 2.3. Що відбувається під капотом (коротко)

1. Два локи: per-job (той самий трек+агент уже біжить → `status: skipped`) і репо-широкий git-лок (`logs/locks/git.lock`) навколо git-секцій — щоб collector і analyst, запущені одночасно (наприклад, launchd доганяє обидва розклади після сну), не ламали git-стан один одному. Локи стійкі до вбитих процесів: застарілий лок (старший за таймаут прогону + 15 хв) або лок мертвого/підміненого процесу перехоплюється автоматично.
2. Прибирання після можливого краху попереднього прогону: незавершений `rebase` абортується, покинутий `.git/index.lock` (без живого git-процесу) видаляється. Якщо HEAD не на `main` (наприклад, застряглий quarantine-checkout) — прогін зупиняється зі `status: error` і чекає твого ручного втручання, нічого не чіпаючи.
3. Git-гігієна: брудне робоче дерево на старті сташується (з міткою `runner:<run_id>`) — **не видаляється**. Кількість накопичених stash-ів пишеться в статус (`stash_count`), і щоденний дайджест попереджає, якщо їх > 0 — розбирай `git stash list` вручну, нічого автоматично не зникає.
4. Виклик CLI без Bash/git-доступу — агент може лише читати й писати файли реєстру/логів, не може сам закомітити чи запушити щось, не бачить жодних токенів/секретів середовища.
5. Guard проти промпт-ін'єкції за **allowlist**: комітиться лише те, що агент має право міняти (`registries/`, `logs/runs|status|decisions`, `agents/catalogs/`, `agents/criteria/criteria*`, `agents/criteria/search-queries.md`, `agents/criteria/taxonomy.md`, `agents/criteria/availability.md`). **Будь-який інший** змінений чи новий шлях — `agents/scripts/`, `agents/prompts/`, `agents/launchd/`, `.gitignore`, `docs/`, корінь репо, `.github/`, нові файли в `.git/hooks` — автоматично відкочується, потрапляє в `blocked_paths` і дає `status: blocked_paths`; диф зберігається окремо для твого перегляду (див. розділ 4 нижче).
6. Коміт одним батчем + push із 3 спробами (`pull --rebase` → `push`; невдалий rebase щоразу абортується, щоб не лишати репо в підвішеному стані). Якщо CLI впав з помилкою — часткові результати комітяться в окрему гілку `quarantine/<run_id>`, **не пушаться**, основна гілка лишається чистою.

## 3. Launchd: постановка й зняття з автопілоту

### 3.1. Підготувати чергу M1 один раз

Виконай `shared/migrations/2026-07-31-job-queue.sql` у Supabase SQL Editor. Якщо
в `~/.config/ideas-scout/env` уже є `SUPABASE_DB_URL`, те саме робить команда:

```
./shared/migrations/apply.sh shared/migrations/2026-07-31-job-queue.sql
```

Міграція створює `jobs`, атомарний `claim_next_job` і додає таблицю до Supabase
Realtime. Повторно її не запускай.

Перед першим прогоном глибокого дослідження виконай ще одну міграцію —
`shared/migrations/2026-08-03-no-market-rejection-code.sql` (те саме через
`apply.sh`). Вона додає значення `NO_MARKET` у CHECK-констрейнт
`ideas.rejection_code`: критерій 4 треку `app-ideas` («Розмір ринку і попит»)
призначає саме цей код, а без міграції запис картки впаде з помилкою
констрейнта на найпершому ж дослідженні ідеї цього треку.

На M1 також потрібен Node.js із `npm`. Installer шукає їх у звичайному `PATH`,
`/opt/homebrew/bin`, `/usr/local/bin` і `~/.local/bin`. Якщо Homebrew уже є, але
Node.js немає: `/opt/homebrew/bin/brew install node`.

### 3.2. Поставити

```
./agents/scripts/install-launchd.sh
```

Скрипт сам попереджає, що це має відбуватись на M1. Він:
- встановлює Node-залежності job-worker-а, якщо їх ще немає;
- рендерить `agents/launchd/*.plist` (підставляє реальний шлях репозиторію замість `__REPO__`);
- кладе результат у `~/Library/LaunchAgents/`;
- перевіряє кожен файл через `plutil -lint` перед завантаженням;
- виконує `launchctl bootstrap gui/$UID <plist>`.

Розкладні джоби мають `RunAtLoad=false`. Лише `job-worker` — постійний демон з
`RunAtLoad=true` та `KeepAlive=true`; окремого Telegram polling-процесу більше немає.
Якщо M1 спав у запланований час,
launchd виконає розкладний джоб при пробудженні — але захист робочих годин
(розділ 2.2) не дасть такому catch-up-прогону з'їсти підписку вдень.

| Джоб | Розклад | Що робить |
|---|---|---|
| `com.ideas-scout.passive-income-collector` | Пн/Ср/Пт, 03:00 | `runner.sh --track passive-income --agent collector --provider claude` |
| `com.ideas-scout.passive-income-analyst` | Вт/Чт/Сб, 05:00 | `runner.sh --track passive-income --agent analyst --provider claude` |
| `com.ideas-scout.monitor` | Щодня, 09:30 | `monitor.sh` |
| `com.ideas-scout.job-worker` | Постійно | Realtime-черга `jobs` → локальні allowlisted скрипти |

Трек `app-ideas` свідомо відсутній у launchd — критерії оцінки для нього (`agents/criteria/criteria-apps.md`) ще порожні (v0.0). Додати відповідні plist-и й рядок у список джобів із порогами свіжості в `agents/scripts/doctor.sh` (секція «Прогони агентів»), коли трек активується.

### 3.3. Перевірити, що встановлено

```
launchctl print gui/$(id -u)/com.ideas-scout.passive-income-collector
launchctl print gui/$(id -u)/com.ideas-scout.job-worker
```

Для наскрізного інфраструктурного тесту:

```
./agents/scripts/enqueue-dry-run.sh
```

За приблизно 10 секунд на `/runs` з'явиться `infrastructure-dry-run` зі статусом
`dry_run`, а відповідний рядок у блоці «Черга M1» стане «Успішно». Лог worker-а:
`logs/launchd/job-worker.launchd.log`.

Глибоке дослідження ідеї — ручний цикл, а не кнопка «зроби все». Автоматичний
мульти-CLI конвеєр демонтовано: повноцінний веб-пошук із CLI має лише codex,
gemini на безкоштовному плані шукає не по-справжньому, а deepseek віддає
закешоване — тобто «кілька незалежних думок» на ділі були однією живою і двома
завченими. Тепер живий пошук роблять браузерні deep-research UI, до яких у
власника є доступ, а M1 лишає собі те, що вміє добре: зведення.

Порядок роботи:

1. На сторінці ідеї скопіювати згенерований промпт глибокого дослідження
   (шаблон — `agents/prompts/deep-research-handoff.md`, підстановка —
   `dashboard/src/lib/deep-research-prompt.ts`).
2. Вставити його в deep-research режим кількох моделей (ChatGPT, Gemini,
   Perplexity, Grok…). Перед вставкою замінити `{{RESEARCHER_LABEL}}` на назву
   моделі — за цією міткою портал потім розкладе відповіді по вкладках.
3. Дочекатись відповідей, скопіювати їх усі одним текстом назад на портал
   (форма консолідації). Портал ріже блоб по маркерах
   `===== DEEP RESEARCH REPORT START | <мітка> | <idea_id> =====` …
   `===== DEEP RESEARCH REPORT END =====`, показує розбір і лише після
   підтвердження пише звіти в `research_reports` і ставить у чергу job
   `deep_research_synthesis`.
4. Worker на M1 запускає `agents/scripts/deep-research.sh --stage synthesis`
   (оркестрація — `agents/scripts/deep-research.py`). Синтез — це **два
   послідовні виклики Claude**, а не один:
   - **виклик A, «прогалини і адʼюдикація»** (промпт
     `agents/prompts/deep-research-synthesis.md`): по базових критеріях Claude
     нічого не досліджує сам, а лише судить чужі докази проти початкового
     аналізу картки; по семи `d_`-блоках, яких у початковому аналізі не було
     взагалі, він спершу шукає у вебі власними WebSearch/WebFetch і лише потім
     звіряє знайдене зі звітами моделей. До власних знахідок діють ті самі
     вимоги «URL плюс дата публікації» — інакше свій звіт завжди виглядав би
     переконливішим за чужий. Результат: вердикт по кожному критерію і
     запропоновані поля картки;
   - **виклик B, «текст картки і конкуренти»** (промпт
     `agents/prompts/deep-research-card.md`): бере готові вердикти виклику A,
     сирі списки конкурентів з усіх звітів і поточне тіло картки — пише повний
     текст розділів «Аналіз за критеріями» і «Конкуренти» та зводить конкурентів
     у єдиний дедуплікований реєстр.

   Розділення саме таке тому, що одна відповідь, яка мала б умістити і
   дослідження, і вердикти, і повну прозу картки, і конкурентів, обривається на
   півслові. Обидва виклики виконуються **завжди**, навіть якщо фатальні
   критерії провалено: власнику потрібен повний пакет (конкуренти, економіка),
   а не самий лише код відхилення. Стеля виконання job-а — 90 хвилин,
   heartbeat воркера щохвилини продовжує lease.

Модель, у якої немає живого пошуку, зобовʼязана відповісти одним рядком
`SEARCH UNAVAILABLE` замість здогадок із памʼяті — такий звіт зберігається зі
статусом помилки й у синтез не йде. Це навмисно: відповідь із памʼяті виглядає
як дослідження, але псує зведений вердикт.

Результат видно в черзі `/runs` як «Синтез глибокого дослідження · <idea_id>»,
run зі статусом `ok` при успіху. Але сам вердикт — не в run, а в трьох
таблицях Supabase: `research_reports` (вербатим-звіти моделей і звіт синтезу —
один рядок `provider: claude`, у якому лежать обидва виклики під заголовками
«Виклик A» і «Виклик B»; читай сюди, коли треба зрозуміти, чому вердикт саме
такий), `criteria_verdicts`
(структуровані рядки по кожному критерію: хто який вердикт поставив, чим
підкріплено, як розв'язано розбіжність) і `competitors` (канонічний список
конкурентів після синтезу). Повний опис полів — розділ «Глибоке дослідження» в
`shared/contracts.md`.

Якщо прогін завершився `status: error` на `/runs` — спершу глянь
`runs.meta.stdout`/`meta.stderr` (те саме, що лежить у логу воркера), а тоді
`research_reports` для цього `idea_id`: рядок зі `status: error` і повним
текстом часто пояснює, що саме пішло не так, ще до того, як довелось парсити
хвіст логів руками.

### 3.4. LLM CLI на M1 для синтезу

Дослідників M1 більше не запускає, тому codex і gemini CLI для глибокого
дослідження не потрібні. Синтез робить той самий `claude`, яким уже
користуються `runner.sh`/`monitor.sh`, через `agents/scripts/llm-invoke.sh`.
Перевірити доступність провайдерів:

```
./agents/scripts/llm-invoke.sh check claude
```

`./agents/scripts/doctor.sh` окремою секцією «Глибоке дослідження» звіряє
наявність шаблона handoff-промпта з маркерами, наявність обох промптів синтезу,
наявність `claude` на хості воркера і стан таблиць дослідження.

Окремо є повільна перевірка, чи `claude` через `llm-invoke.sh` справді ходить у
веб:

```
./agents/scripts/doctor.sh --websearch
```

Вона просить модель знайти пошуком свіжу новину й повернути URL із датою. Якщо
у відповіді немає ні URL, ні дати — чек червоний, бо це саме той тихий збій, від
якого страждає весь ручний цикл: синтез усе одно відпрацює й випише вердикти,
але `d_`-блоки заповнить із памʼяті замість живого пошуку. Перевірка коштує
виклику моделі й кількох хвилин, тому за замовчуванням не виконується.

**Змінні середовища конвеєра** (усі опційні, з розумними дефолтами):

| Змінна | За замовчуванням | Що робить |
|---|---|---|
| `IDEAS_SCOUT_SYNTHESIS_TIMEOUT_S` | `2700` | Таймаут виклику A (адʼюдикація плюс власний веб-пошук по `d_`-блоках) — він більший саме через реальний пошук |
| `IDEAS_SCOUT_SYNTHESIS_CARD_TIMEOUT_S` | `1800` | Таймаут виклику B (текст картки і зведення конкурентів) |
| `LLM_INVOKE_TIMEOUT_S` | `1800` | Дефолтний таймаут усередині `llm-invoke.sh run`, якщо викликати його напряму |
| `IDEAS_SCOUT_DEEP_RESEARCH_DRY_RUN` | — | `1` вимикає виклики LLM і лишає лише інфраструктурний прогін ланцюжка портал→воркер→скрипт (успіх за `IDEAS_SCOUT_DEEP_RESEARCH_DRY_RUN_DELAY_SECONDS`, дефолт 10с) |

### 3.5. Зняти

```
./agents/scripts/install-launchd.sh --uninstall
```

Виконує `launchctl bootout` для кожного джоба й видаляє plist-и з `~/Library/LaunchAgents/`.

## 4. Як читати логи й статуси

### 4.1. `logs/status/<track>-<agent>.json`

Один файл на джоб (не один спільний файл — щоб паралельні прогони різних джобів не били по тому самому файлу). Поля:

- `status`: `ok` (усе пройшло, закомічено й запушено або принаймні закомічено), `error` (CLI впав — див. `error_tail`, шукай гілку `quarantine/<run_id>`; або HEAD був не на main; або codex без явного дозволу), `skipped` (per-job або git-лок був живий, прогін пропущено), `skipped_work_hours` (прогін припав на робоче вікно — захист підписки, див. розділ 2.2), `blocked_paths` (guard відкотив зміни поза allowlist — див. нижче), `dry_run`.
- `push`: `ok` / `failed` (спроби вичерпано, зміни лишились локальними) / `skipped` (нічого комітити, або офлайн, або dry-run).
- `offline`: `true`, якщо remote був недоступний на момент прогону.
- `stash_count`: скільки stash-ів накопичилось у репозиторії (0 в нормі; >0 — розібрати `git stash list` вручну, дайджест теж попередить).
- `blocked_paths`: перелік шляхів, які guard відкотив (порожньо в нормі).
- `error_tail`: хвіст виводу CLI, якщо `cli_exit_code != 0`.

### 4.2. `logs/launchd/<track>-<agent>.log`

Повний накопичувальний лог кожного прогону цього джоба (стдаут+стдерр, з датою на старті кожного запуску). Сюди ж дублюється те, що бачить `launchd` через `StandardOutPath`/`StandardErrorPath` (окремий `.launchd.log` — там лише сирий вивід самого launchd-виклику).

### 4.3. `logs/quarantine/<run_id>-blocked-paths.diff`

З'являється лише коли guard щось відкотив. Це і є той «переглянути відкочені зміни руками» момент.

### 4.4. Що робити при `status: blocked_paths`

Це найважливіший статус, на який варто реагувати не відкладаючи — він означає, що прогін спробував змінити щось поза дозволеною зоною (allowlist: реєстр, логи прогонів, каталоги, критерії — повний перелік у розділі 2.3, п.5), а це найімовірніше або баг у промпті, або **успішна спроба промпт-ін'єкції** з зовнішнього контенту (Reddit-коментар, сторінка, транскрипт), який агент читав. Заблоковані файли з дифом лежать у `logs/quarantine/` — ця тека в `.gitignore`, потенційно атакерський вміст ніколи не потрапляє в git-історію.

1. Відкрий `logs/quarantine/<run_id>-blocked-paths.diff` — там повний диф/вміст того, що система відмовилась комітити.
2. Подивись, звідки міг узятися цей вміст — які URL/джерела оброблялись у цьому прогоні (`logs/runs/<run_id>*.md`, якщо він встиг створитись).
3. Реальна шкода вже відвернута (зміни відкочені, нічого не запушено) — це розслідування постфактум, не аварійна ситуація.
4. Якщо це виявився легітимний баг промпту (агент сам вирішив, що йому треба поправити конфіг) — виправ промпт вручну, це не інфраструктурна проблема.

### 4.5. `logs/status/monitor.json`

Пише сам `monitor.sh` після щоденного прогону: чи вдалось надіслати дайджест у Telegram, чи спрацював healthcheck-пінг, скільки записів реєстру змінилось за 24 год.

### 4.6. `logs/runs/reddit-cache/`

Сирі дампи Reddit, які `agents/scripts/reddit-fetch.sh` кладе перед кожним прогоном collector-а (`latest/*.json` + `_meta.md`). Локальний стан машини, у `.gitignore`, у git не потрапляє.

## 6. Секрети — де і чого немає

Токен Telegram-бота, chat_id і healthcheck-URL живуть **лише в Keychain** (`security add-generic-password`). Секрет перевірки webhook живе як `TELEGRAM_WEBHOOK_SECRET` у Vercel Environment Variables і в `~/.config/ideas-scout/env` на M1; у Git його немає. У `agents/launchd/*.plist` і логах жодного з цих значень немає й бути не повинно. `monitor.sh` передає токен і healthcheck-URL у curl через config на stdin (`-K -`), а не через аргументи командного рядка — аргументи будь-якого процесу видно всім локальним процесам у `ps aux`, stdin — ні. `runner.sh` і `monitor.sh` навмисно не передають агенту (`claude -p`) жодних інструментів для запуску довільних команд — тож навіть теоретична компрометація промпту зовнішнім контентом не дає агенту шляху до Keychain чи до `gh`/git-токенів (саме тому `--provider codex`, чия пісочниця дає shell, вимкнено за замовчуванням).

## 7. Тижневий ритм: що має статись і як ловити поломку

### Здоровий тиждень

За тиждень система має зробити приблизно таке:

- **3 прогони збирача** (пн/ср/пт 03:00) — кожен лишає файл у `logs/runs/` і власний коміт «Прогін …» у GitHub;
- **3 прогони аналітика** (вт/чт/сб 05:00) — кожен додає до 5 записів у `registries/passive-income/ideas/` і рядки в `logs/dedup-decisions.md`;
- **7 дайджестів** у Telegram (щодня 09:30);
- у сумі — приблизно 5–15 нових записів реєстру, з них одиниці доходять до `approved_pending`. Це нормальна пропорція: більшість ідей мають відсіюватись, інакше критерії надто м'які.

### Твоя участь — приблизно 10 хвилин на тиждень

1. Раз на день глянути дайджест (лише на предмет попереджень — деталі не потрібні).
2. Раз на тиждень відкрити свіжий індекс і подивитись, що накопичилось:
   ```
   ./agents/scripts/generate-index.sh passive-income && open registries/passive-income/ideas.md
   ```
3. Ухвалити рішення по записах зі статусом `approved_pending` і по тих, де стоїть `ceiling_flag: review` — це ідеї, які система свідомо не стала відхиляти сама, бо рішення «чи варта гра свічок» лишається за тобою. Кожне таке рішення поступово перетворюється на правило в критеріях.

### Одна команда, коли щось здається не так

```
./agents/scripts/doctor.sh
```

Перевіряє все за один прохід і пояснює людською мовою: чи не присипляє себе M1
(закрита кришка — найчастіша причина «бот не відповідає»), чи всі launchd-джоби на
місці, чи працює постійний job-worker і чи тримається його Realtime-канал, чи
відповідає Supabase і чи не накопичується черга завдань, чи на місці секрети в
Keychain, чи зареєстрований Telegram-webhook і чи не відбиває його Telegram, чи не
протух логін до Claude, і в якому стані репозиторій.

Окрема секція — **глибоке дослідження**. Вона ловить те, що інакше зникає тихо:
чи встановлені всі дослідницькі моделі (бо кнопка спрацює й тоді, коли половини
з них немає — просто вердикт спиратиметься на менше незалежних джерел, а в цьому
й був увесь сенс), чи накочена міграція нових таблиць (без неї моделі відпрацюють
30–90 хвилин, а записати результат буде нікуди), і чи не сипляться звіти окремих
моделей та самі запуски дослідження за останній тиждень.

Там же врахована особливість, через яку doctor раніше бив би хибну тривогу:
воркер бере завдання по одному, а глибоке дослідження триває до 90 хвилин, тож
черга за ним стоїть законно. Тепер це попередження «черга чекає на глибоке
дослідження», а не «черга стоїть» — але лише поки той джоб реально живий
(тримає lease). Якщо воркер помер посеред дослідження, це знову ✘, як і має бути.

Скрипт лише читає — його безпечно запускати будь-коли, зокрема посеред нічного
прогону. Виходить кодом 0 (чисто), 1 (є попередження) або 2 (щось зламано).

Два прапорці: `--offline` пропускає мережеві перевірки, `--llm` додатково робить
реальний виклик `claude -p` — єдина по-справжньому надійна перевірка логіну, але
вона витрачає ліміт підписки, тому не входить у звичайний запуск.

Третій, `--baseline-clamshell`, — єдиний, що пише (позначку часу в
`~/.config/ideas-scout/clamshell-baseline`) і одразу виходить. Журнал живлення
накопичувальний: засинання від кришки, що були **до** `sudo pmset -a disablesleep 1`,
лишаються в ньому назавжди й вічно тягнуть ▲, через що справжній рецидив нічим не
відрізнити від старої історії. Запусти цей прапорець один раз одразу після
`pmset` — далі doctor рахує лише пізніші засинання, і ▲ знову означає «фікс
злетів». Стару кількість він при цьому показує довідково.

Запускати треба **на M1 під агентським юзером** — саме там живуть джоби, секрети й
воркер. На іншій машині скрипт це розпізнає й позначить нерелевантні перевірки як
довідкові, а не як поломки.

### Ознаки поломки — від найтривожнішої

| Що бачиш | Що це означає | Перша дія |
|---|---|---|
| **Дайджест не прийшов узагалі** | Найгірший сигнал: M1 спить, сесія агента вилогінена, launchd знято або сам монітор упав. Мовчання = поломка, а не «все спокійно» | `launchctl list \| grep ideas-scout`, потім `pmset -g assertions` |
| `status=blocked_paths` | Прогін намагався записати щось поза дозволеними теками — можлива спроба промпт-ін'єкції з веб-контенту. Зміни вже відкочені й не закомічені | Прочитати `logs/quarantine/<run_id>-blocked-paths.diff` **очима**, перш ніж щось із цим робити |
| `status=error` | Виклик моделі впав або вичерпав таймаут. Часткові результати лежать у гілці `quarantine/<run_id>` і не запушені | `tail -40 logs/launchd/<джоб>.log` |
| `push=failed` | Робота збережена локально, але не доїхала в GitHub: проблема з SSH-ключем або мережею. Коміти накопичуються на M1 | `ssh -T git@github.com`, потім `git -C ~/Projects/ideas-scout push` |
| «давно не запускався» (поріг 72 год) | Джоб не спрацював: машина спала в момент розкладу або джоб знято | Перевірити `pmset -g sched` і `launchctl list` |
| `skipped_work_hours` регулярно | Розклад джоба конфліктує з твоїм вікном заборони (`agents/criteria/availability.md`) | Рознести їх: змінити годину в plist або вікно в змінних |
| «Записів додано за 24 год: 0» кілька разів поспіль | Збирач нічого не знаходить: джерело деградувало (типово — блокування) або патерни вичерпались | Прочитати секцію «Стан джерел» у свіжому `logs/runs/*.md` |

### Чого система поки НЕ вміє

- **Трек `app-ideas` вимкнений** — критерії для нього порожні (`criteria-apps.md` v0.0), джоба немає.
- **Codex як провайдер заблокований** — його пісочниця дає агенту shell, що ламає межу безпеки; вмикається лише явним `IDEAS_SCOUT_ALLOW_CODEX=1`.

## 8. Ручне подання ідей через Telegram-бота

Той самий бот, що шле дайджест, приймає й твої власні ідеї: кидаєш посилання, думку чи
скріншот — і за кілька хвилин отримуєш вердикт за тими самими критеріями. Поведінка бота
в чаті описана окремо: [telegram-bot-ux.md](telegram-bot-ux.md).

### 8.1. Що це технічно

Telegram надсилає update у `/api/telegram/webhook` дашборда на Vercel. Route звіряє
секретний заголовок `X-Telegram-Bot-Api-Secret-Token`, перевіряє розмір і формат,
після чого швидко створює `telegram_update` у таблиці `jobs`. `update_id` стає
idempotency key, тому повторна доставка Telegram не запускає подію двічі.

Постійний `job-worker` на M1 прокидається через Supabase Realtime, атомарно забирає
job і запускає `agents/scripts/telegram-bot.py --process-update`. Update передається
JSON-ом через stdin. Бот бере токен і `chat_id` з того самого Keychain, що й
`monitor.sh`, і додатково обробляє **лише** свій `chat_id`: навіть справжня подія з
чужого чату не може запустити тріаж. Для незавершеної чернетки webhook також ставить
відкладену `telegram_nudge`; це job у Supabase, а не опитування Telegram.

Сам бот нічого не оцінює й не має справи з git. Він збирає повідомлення в чернетку,
за твоїм підтвердженням кладе її в `inbox/<draft_id>-<track>/` і викликає
`runner.sh --track <track> --agent triage --provider claude`. Далі — звична межа
безпеки: агент без Bash, коміт робить runner.

### 8.2. Налаштування webhook

1. Згенеруй один секрет: `openssl rand -hex 32`.
2. Додай його у Vercel як `TELEGRAM_WEBHOOK_SECRET` для Production, а поряд —
   `TELEGRAM_CHAT_ID` зі значенням із Keychain (`ideas-scout-telegram-chat`), і зроби
   redeploy. Без `TELEGRAM_CHAT_ID` webhook відповідає 503 і нічого не приймає.
3. Додай **те саме** значення секрету в `~/.config/ideas-scout/env` на M1:
   `TELEGRAM_WEBHOOK_SECRET=<значення>`.
4. На M1 після `git pull` повторно виконай `./agents/scripts/install-launchd.sh`.
   Installer сам зупинить і видалить старий `com.ideas-scout.telegram-bot` long-polling
   agent, якщо той був установлений; постійним лишиться `job-worker`.
5. Зареєструй адресу вже задеплоєного дашборда в Telegram:

```
./agents/scripts/configure-telegram-webhook.py https://<твій-домен-vercel>
```

Скрипт читає токен і chat_id з Keychain, секрет з env-файлу, викликає `setWebhook`,
ставить список команд бота лише для твого чату (для решти чатів команди видаляє,
тож стороння людина не бачить меню) і перевіряє результат через `getWebhookInfo`.
Токен і секрет не друкуються. Після цього надішли боту `/status`: на `/runs` мають з'явитися
`telegram-update` job і пов'язаний run зі статусом `ok`.

### 8.3. Де що лежить

| Що | Де | Комітиться |
|---|---|---|
| Поточна чернетка, ще не підтверджені файли | `~/Library/Application Support/ideas-scout/` | ні — і навмисно поза репо |
| Підтверджений матеріал (текст, скріншоти, збережені сторінки) | `inbox/<draft_id>-<track>/` | так |
| Рядки прогресу для чату | `logs/triage/<draft_id>.progress` | ні (gitignored) |
| Вердикт для чату | `logs/triage/<draft_id>.md` | так |
| Сама картка | `registries/<track>/ideas/` | так |

Рантайм-стан бота лежить поза репозиторієм не з естетики: guard `runner.sh` відкочує
будь-який шлях поза allowlist, а гігієна на старті прогону робить `stash` — усередині
репо цей стан не пережив би нічний прогін. З тієї ж причини `inbox/` і `logs/triage/`
явно додані і в allowlist, і у виключення `stash` (матеріал пишеться **до** старту
прогону тріажу, інакше прогін з'їв би власний вхід).

Зв'язок «повідомлення з вердиктом → картка» ніде не зберігається: коли ти відповідаєш
на старий вердикт, бот читає id картки прямо з тексту цитованого повідомлення.

### 8.4. Відмінності тріажу від інших агентів

- **Захист робочих годин на нього не діє** — його завжди ініціюєш ти вручну з чату, і
  мовчазний `skipped_work_hours` виглядав би як зависання бота.
- **Таймаут 15 хв**, а не 45 — оцінюється рівно один матеріал, і ти чекаєш у чаті.
- **Вимагає `IDEAS_SCOUT_INBOX_FILE` і `IDEAS_SCOUT_DRAFT_ID`** (їх передає бот). Шлях
  приймається лише у формі `inbox/…` без `..` — щоб цим не можна було націлити агента
  на довільний файл машини.

### 8.5. Коли щось не так

| Що бачиш | Що це означає | Перша дія |
|---|---|---|
| Бот мовчить, job не з'явився | Webhook не зареєстрований або Vercel відхиляє секрет | Запусти `configure-telegram-webhook.py` ще раз; перевір Vercel env і redeploy |
| `telegram_update` стоїть у черзі | M1 спить або job-worker не запущений | `launchctl print gui/$(id -u)/com.ideas-scout.job-worker`; потім лог `logs/launchd/job-worker.launchd.log` |
| `telegram_update` має `failed` | Одноразовий handler або triage впав | Відкрий `last_error` на `/runs` і `tail -40 logs/launchd/job-worker.launchd.log` |
| «Оцінка не завершилась (код …)» | `runner.sh` або CLI впали — матеріал у `inbox/` лишився | `tail -40 logs/launchd/app-ideas-triage.log` |
| Панель зависла на «Оцінюю…» | Агент не пише `logs/triage/<id>.progress` | Дочекатись таймауту (15 хв), потім подивитись лог джоба |
| Бот пише «Чекаю, зайнято іншим прогоном» | Саме йде нічний прогін і тримає git-лок | Нічого — стане в чергу сам |
| «Попередня оцінка урвалась» | M1-worker або handler перезапустився під час прогону; матеріал цілий | Натиснути «Повторити» |
