# Критерії оцінки: мобільні застосунки

Версія: v0.1 — ЧЕРНЕТКА, не затверджена власником
Дата: 2026-07-29

**Статус треку: вимкнений.** Джоби для app-ideas (збирач, аналітик) не ставляться в розклад, поки власник не пройде розділ «Що затвердити власнику перед увімкненням треку» в кінці цього файлу і явно не підніме версію до v1.0. До того момента цей файл — робоча чернетка для обговорення, не діючий чек-лист.

Джерело: PLAN.md, Фаза 2 (кінець розділу) — «для criteria-apps.md — окремий чек-лист (розмір ринку, конкуренція, монетизація; зусилля очікувані, не мінімізовані)». Структура файлу свідомо копіює `config/criteria-passive-income.md` (v0.3): нумеровані критерії, кожен з полями «що перевіряти / що вважається провалом / rejection_code», порядок від дешевих перевірок до дорогих, зупинка на першому фатальному провалі. Але змістовно критерії інші — див. розділ нижче про ключову відмінність треку.

**Ключова відмінність від треку passive-income:** там головний фільтр — автономність (чи проживе механіка без нагляду власника). Тут — навпаки: застосунок будується руками, зусилля розробки й підтримки — ОЧІКУВАНІ, не мінімізовані. Тому в цьому чек-листі немає аналога критерію «Автономність» — його місце займає «Очікувані зусилля» (критерій 7), який лише вимірює обсяг роботи для планування, а не відхиляє ідеї за те, що вони вимагають рук.

## 0. Гіпотеза цінності (лише для `signal_type: automation_report`, фатальний)

**Застосовність:** так само, як критерій 0 у `criteria-passive-income.md` v0.3 — оцінюється тільки для знахідок типу «я автоматизував/зробив собі X» (`signal_type: automation_report`), де автор не описує це як готовий продукт із платниками. Для `signal_type: income_claim` (знахідка вже описує застосунок, що заробляє чи має користувачів) критерій 0 пропускається, чек-лист починається одразу з критерію 1.

**Що робить аналітик:** перш ніж переходити до критерію 1, формулює гіпотезу цінності — яку конкретну проблему користувача застосунок розв'язує, для кого саме, і чому людина відкриє його вдруге (не одноразова цікавість). Записує гіпотезу в поле `value_hypothesis` (аналог `monetization_hypothesis` у passive-income, але тут йдеться про користувацьку проблему, а не одразу про платника — до монетизації дійде критерій 6).

**Що вважається провалом:** неможливо сформулювати чітку користувацьку проблему — ідея є технічною вправою автора («я зробив собі скрипт») без окресленого «для кого» і «навіщо повертатись», без різниці між «цікава демка» і «застосунок, яким хтось буде реально користуватись».

**rejection_code:** `NO_MONETIZATION` (той самий код, що й у passive-income — переносить сенс «немає видимої цінності для когось, хто платитиме увагою чи грошима»; окремого коду для цього треку не заводимо, щоб не плодити паралельні коди з однаковим змістом).

## 1. Довіра до джерела

Успадковано без змін від `config/criteria-passive-income.md` (v0.3, критерій 1) — та сама шкала A–D, ті самі якорі («A» — зовнішньо підтверджені цифри/живий продукт, «B» — самозвіт з live-продуктом і трек-рекордом без зацікавленості, «C» — самозвіт без верифіковного продукту чи з м'якою зацікавленістю, «D» — цифри як маркетинговий аргумент продавця курсу/інструменту). Дивись оригінал у passive-income за деталями формулювань — тут не дублюється текстом, щоб уникнути розбіжностей при майбутньому тюнингу однієї копії без іншої.

**Що вважається провалом:** оцінка джерела D за шкалою A–D.

**rejection_code:** `SOURCE_SUSPECT`

## 2. Легальність і політики платформ (фатальний)

**Що перевіряти:**

- **Легальність ідеї в ЄС/Іспанії** — сама механіка застосунку (не залежно від того, хто й коли її реалізує) не порушує закон: обробка персональних даних, вікові обмеження контенту, регульовані сфери (фінанси, здоров'я, азартні механіки тощо).
- **Відповідність App Store Review Guidelines** — типові категорії, які Apple системно відхиляє чи ставить під посилений розгляд: застосунки-обгортки над чужим вебсайтом без доданої цінності, спам-клони існуючих застосунків, контент для дорослих без вікового гейту, криптовалютний майнінг на пристрої, азартні ігри без ліцензії, медичні поради без застереження. Також обмеження на використання приватних/недокументованих API iOS — якщо ідея технічно спирається на щось, чого Apple не дозволяє викликати з публічного SDK, це вбиває ідею на рівні платформи, а не ринку.
- **GDPR**, якщо застосунок збирає будь-які персональні дані користувача (навіть email для реєстрації): потрібна політика приватності, правова підстава обробки, механізм видалення даних на запит користувача.

**Що вважається провалом:** механіка нелегальна або в правовій сірій зоні в ЄС/Іспанії; або застосунок потрапляє в категорію, яку Apple типово відхиляє чи вимагає складної додаткової верифікації (наприклад, ліцензії) недосяжної соло-розробнику; або збір персональних даних без реалістичного плану виконати вимоги GDPR.

**rejection_code:** `LEGAL`

## 3. Реалізовність соло-розробником наявними засобами

**Що перевіряти:**

- Чи будується застосунок однією людиною з парним програмуванням через AI (Claude Code / Codex) на Mac M1/M5 — тобто чи покривається технічний стек поточним станом `catalogs/ai-capabilities.md` (мова, фреймворк, доступні локальні можливості M1/M5, межі того, що AI-асистент реально вміє написати й налагодити без спеціалізованої команди).
- Чи має ідея важкі бекенд-вимоги — власний сервер із серйозним навантаженням, GPU-інференс (наприклад, власна модель генерації зображень чи відео на пристрої користувача чи на сервері), реалтайм-інфраструктура (стрімінг, live-матчмейкінг) — усе, що вимагає або окремої DevOps-роботи, або обчислювальних ресурсів поза межами того, що описано в розділі «Локальні можливості M1/M5» каталогу можливостей.
- Чи потрібна докупка інструментів/сервісів/підписок понад поріг €100 (одноразово чи як регулярна стаття витрат) — приклад-межа: Apple Developer Program, $99/рік, необхідний для публікації в App Store. Це прикордонний випадок відносно порогу — **потребує погодження власника** явно щоразу, коли ідея впирається саме в цю статтю (див. розділ рішень унизу файлу: чи вважати цю конкретну витрату одноразово наперед погодженою для всього треку, чи ні).

**Що вважається провалом:** бракує можливості, якої немає в `ai-capabilities.md` і не з'явиться в найближчому горизонті (важкий бекенд/GPU-навантаження, недоступне на M1/M5 чи в межах підписок) → `CAPABILITY_GAP`; або сумарна докупка перевищує €100 без отриманого погодження → `CAPITAL` (запис лишається в `analyzing` до рішення власника, а не автоматично відхиляється — так само, як у критерії 3 passive-income).

**rejection_code:** `CAPABILITY_GAP` | `CAPITAL`

## 4. Розмір ринку і попит

**Що перевіряти:** ознаки реального попиту — пошуковий обсяг за релевантними запитами (наскільки часто люди шукають рішення саме цієї проблеми), рейтинги й кількість відгуків у конкуруючих застосунках (жива категорія має живих конкурентів із тисячами відгуків, а не порожню полицю), повторювані скарги в рев'ю конкурентів (скарги — сильніший сигнал попиту на покращення, ніж похвали: показують, що люди платять і незадоволені чимось конкретним, що можна виправити).

**Що вважається провалом:** мікроніша без ознак платоспроможної аудиторії — жодного пошукового обсягу, жодного конкурента з помітною кількістю користувачів, або аудиторія настільки вузька, що навіть 100% захоплення ніші не дає осмисленого результату (ні доходу, ні портфоліо-цінності).

**rejection_code:** `NO_MARKET` *(новий код для цього треку — відсутній у списку кодів passive-income, бо там аналог цієї перевірки не потрібен: пасивний дохід не завжди прив'язаний до «ринку застосунків» у класичному розумінні. Тут же «розмір ринку» — самостійна вісь, тому отримує власний код, а не переносить сенс якогось іншого.)*

## 5. Конкуренція і диференціація

**Що перевіряти:** скільки застосунків уже розв'язують саме цю проблему; чи є в ідеї кут диференціації, який соло-розробник реально здатен втримати проти команд (не «зробимо те саме, але красивіше» — це не втримується проти ресурсів конкурента, а щось на кшталт вужчої спеціалізації, кращого разового досвіду, локальної/приватної обробки даних тощо); чи не з'їдає нішу безкоштовне системне рішення від Apple чи Google (наприклад, ідея-таймер поверх того, що вже безкоштовно робить стандартний застосунок «Годинник», чи нотатки поверх системних «Нотаток» — Apple регулярно забирає такі ніші новою версією ОС).

**Що вважається провалом:** ніша вже щільно заповнена подібними застосунками без реалістичного кута диференціації, який соло-розробник утримає; або функціонал імовірно опиниться безкоштовно в наступній версії iOS/Android чи вже покритий системним застосунком.

**rejection_code:** `SATURATED`

## 6. Монетизація (нефатальний, `ceiling_flag`)

**Статус:** нефатальний критерій, аналогічний критерію 6 у passive-income — не відхиляє записи і сам по собі не має `rejection_code`.

**Що робить аналітик:** визначає модель монетизації (платний застосунок наперед, підписка, разові покупки всередині застосунку — IAP, реклама, або комбінація); оцінює реалістичний діапазон доходу для інді-застосунку цієї категорії (спираючись на публічні дані про подібні застосунки, де доступні — рейтинг у топ-чартах категорії, орієнтовні оцінки завантажень); оцінює готовність цільової аудиторії платити за рішення цієї конкретної проблеми (є категорії, де користувачі звикли платити — продуктивність, здоров'я; є категорії, де очікування «все безкоштовно» майже непереборне).

**Що робить система:** запис, де монетизація виглядає слабкою відносно реального попиту (є попит, критерій 4 пройдено, але грошей із цього не витягнути) — нефатально, позначається `ceiling_flag: review` і виноситься власнику в дайджест на ручну оцінку, так само як у passive-income. Записи без сумнівів щодо монетизації лишають `ceiling_flag: null`.

**rejection_code:** немає (нефатальний критерій).

## 7. Очікувані зусилля (нефатальний, інформаційний)

**Статус:** нефатальний, чисто інформаційний критерій — на відміну від критерію «Автономність» у passive-income, тут високі зусилля НЕ є підставою для відхилення. Це очікувана природа треку: застосунок будується руками.

**Що робить аналітик:** оцінює орієнтовну кількість годин до робочого MVP (мінімальної версії, яку можна показати чи протестувати) і окремо — до першої публікації в App Store (з урахуванням проходження Review, підготовки метаданих, скріншотів, політики приватності). Записує в поле `launch_effort_hours`.

**Що робить система:** зіставляє оцінку з `config/availability.md` (розділ «Години на запуск нового») — не для відхилення, а щоб власник бачив у дайджесті, скільки реальних тижнів роботи ідея забере при поточному бюджеті часу, перш ніж вирішувати, братись за неї чи ні.

**rejection_code:** немає (нефатальний, інформаційний критерій).

## Правила застосування

**Послідовність:** для записів із `signal_type: automation_report` чек-лист починається з критерію 0 (гіпотеза цінності) — провал тут зупиняє аналіз одразу, до критерію 1. Для `signal_type: income_claim` критерій 0 пропускається. Далі критерії проходяться по порядку: 1 → 2 → 3 → 4 → 5. Аналіз зупиняється на першому фатальному провалі серед критеріїв 0, 2, 3, 4, 5 (критерій 1 — фатальний лише на оцінці D, решта оцінок пропускають далі з позначкою на `confidence`). Критерії 6 і 7 — нефатальні й оцінюються тільки для записів, що дійшли до кінця чек-листа без фатального провалу на 0–5; для записів, зупинених раніше, 6 і 7 не оцінюються.

**Правило первинного коду (подвійні провали):** якщо запис одночасно провалює більш ніж один фатальний критерій (наприклад, і `CAPABILITY_GAP`, і `CAPITAL` одночасно, або `NO_MARKET` разом із `SATURATED`), `rejection_code` лишається один — первинний, той, що трапився раніше за порядком проходження. Супутні коди йдуть у поле `rejection_codes_extra` (список), так само як у critera-passive-income. Ревізор при перегляді запису сканує обидва поля.

**Правило `transferred`:** ідея, що прийшла в реєстр app-ideas через `transferred_to` з реєстру passive-income (крос-перекидання за PLAN.md, Фаза 4: «зроби нішевий застосунок» → перенос), зберігає посилання на запис-джерело (той запис у passive-income лишається зі своїм статусом і посиланням назад), але аналіз у цьому реєстрі починається з нуля за ЦИМ чек-листом — жоден вердикт із passive-income (наприклад, пройдений там критерій «Насиченість ринку») не переноситься автоматично, бо критерії різні по суті (там — насиченість механіки заробітку, тут — насиченість застосунків).

## Що затвердити власнику перед увімкненням треку

Перелік конкретних рішень, які цей чек-лист свідомо не приймає сам — трек лишається вимкненим, доки власник не дасть відповідь на кожен пункт (можна одним рядком на пункт):

- **Поріг «немає ринку» (критерій 4, `NO_MARKET`):** які саме числа вважати мінімальним сигналом попиту (наприклад: мінімальна кількість відгуків у топ-3 конкурентах, мінімальний пошуковий обсяг за ключовим запитом) — зараз критерій сформульований якісно («мікроніша без ознак»), без конкретних порогів.
- **Apple Developer Program $99/рік:** чи вважати цю витрату одноразово наперед погодженою для всього треку app-ideas (тобто не питати щоразу, коли ідея впирається саме в цю статтю й більше ні в що понад €100), чи погоджувати окремо для кожної першої ідеї, що доходить до публікації. Наразі позначено як **потребує погодження власника** — рішення не прийняте автоматично.
- **Окремий бюджет часу на трек:** чи `config/availability.md` матиме окремий розділ/цифру годин саме під app-ideas (розробка руками — це інша структура витрат часу, ніж моніторинг пасивного доходу), чи трек ділить той самий загальний бюджет з рештою.
- **Джерела для збирача, специфічні під застосунки:** розділ джерел у PLAN.md (Фаза 3) писаний під passive-income (Reddit r/passive_income, Indie Hackers тощо) — для app-ideas потрібен окремий перелік (наприклад: App Store/Google Play топ-чарти й нові релізи, r/AppIdeas чи r/iOSProgramming, скарги в рев'ю конкурентів, Product Hunt категорія mobile). Цей перелік ще не написаний і не входить у цей файл критеріїв.
- **Явний якір для критерію 5 «Конкуренція»:** скільки саме конкурентів у ніші вважати «щільно заповненою» (число застосунків із помітною тракцією), бо зараз формулювання якісне й лишає широкий простір для суб'єктивної оцінки аналітика.
